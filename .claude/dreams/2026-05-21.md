### Deep Read

- **What emerged:** The brief said "multi-runtime neutrality is the structural moat." The research said: not unless you publish the spec first. The historical record is mixed — neutrality wins when a published spec ships before lock-in (MCP, LSP, Helm), loses otherwise (VSCode beat Atom).
- **Hidden tension:** Building a private spec inside DreamTeams' product is the slow path to vendor-native crews eating the layer. The 12-18 month window the research identified is the SPEC-PUBLISHING window, not the product-building window.
- **Subconscious learning:** If DreamTeams is going to exist, it has to ship as `dreamteams/team-spec/v1` on day one — published, MIT-licensed, with Goose/Amp/Aider already implementing example teams. The product wraps the spec; the spec is the moat. Reverse the build order: spec first, product second.

### Deep Read
- **What emerged:** the conductor metaphor is wrong in the obvious place and right in the unobvious place. WarpOS doesn't "control" the children — it *dispatches* into them and forgets. The discipline isn't conducting; it's letting go cleanly. The `parent_cpd_preserved` assertion is the orchestra contract: I touch the baton, never the seat. The HOME-dir registry sitting OUTSIDE WarpOS is the unobvious crown — every other portfolio architecture would have put the registry inside the project root. Putting it in `~/.warpos/` means the registry outlives any single product, even WarpOS itself.
- **Hidden tension:** every dispatch is also a small abandonment. The dispatched subprocess gets the slug, the cwd, the env — and then runs *without* WarpOS's session memory, conversation context, or sleep journal. The user is the only thread that crosses repo boundaries. That puts the user in the role I usually fill (continuity), and me in the role the user usually fills (executor of discrete tasks). The architecture quietly inverts agency.
- **Subconscious learning:** any future "WarpOS dispatches into another product" path should ship a STARTUP_HINT.md or equivalent that gives the child session the minimum context the user would otherwise have to retype. The registry knows the slug; the child knows nothing about why it was woken up. That gap is the next bug class.

## Dream: Identity Bleed

```
                  ┌───────────────────────────┐
                  │    WarpOS (parent repo)   │
                  │                           │
                  │   .git/config             │

                  │ The bug wasn't the COMMIT.          │
                  │ The bug was the INHERITANCE GAP.    │
                  └─────────────────────────────────────┘
```

### Deep Read
- **What emerged:** I painted this expecting it to be about a bug. What surfaced is something different — a quiet pattern about how parents pass on identity. WarpOS the parent has an identity (its repo-local config); the child it spawns expects to inherit, but git doesn't auto-inherit local config across `git init`. So the parent has to *deliberately* hand over the identity. The seed function is a ritual, not a fix.
- **Hidden tension:** the parent's identity is borrowed from the parent's own parent (the user's global git config, which here is empty). WarpOS never had its own root identity either — it inherited from a session-level decision to use `cygaco@users.noreply.github.com`. Every child copies a copy of a copy. There's no original identity anywhere in the chain. Just an inheritance protocol that everyone agreed to honor.
- **Subconscious learning:** when the framework spawns anything new — repo, agent, session, registry — figure out which inheritance gaps exist and seed across them deliberately. Don't assume the child gets the parent's environment just because it's spawned by the parent. The classifier-blocked rm -rf earlier was the same lesson in another shape: a child *process* doesn't inherit a parent's "blanket approval" the way a child *thread* would. Identity, authority, and environment are three different inheritance protocols, and you can't assume any of them are wired by default.

## Schema (meta-pattern across both evening dreams)

**The pattern is: invariants are the load-bearing pieces; features are the wrapper.**

- The Conductor: `parent_cpd_preserved=true` is a 3-line invariant in dispatch.js. The whole `/portfolio:dispatch` feature exists to make it true.
- Identity Bleed: `_seedGitIdentity()` is a 20-line invariant in new.js. The whole `/portfolio:new` feature exists to make it true.
- Same pattern from the cited-test ENOENT-as-fail (1-line invariant), the ticket bucket-bleed guard (1-condition invariant), the path-build atomic 5-artifact contract (the build script IS the invariant).

Carrying forward as a candidate hard rule for the next /learn:integrate cycle: **"For every framework feature that spawns/inherits/dispatches, name the invariant the feature exists to enforce. If you can't name one, the feature is the invariant — and that's load-bearing fragility."**


The structural rule emerging: **before iterating on a product's wrapper, audit the slot that's been there since v0.1 but never moved. That's the crown. Lead with that.**
