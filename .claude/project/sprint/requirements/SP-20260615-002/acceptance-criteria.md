# Acceptance Criteria — Visual interactive roadmap panel — browser GUI (ROADMAP item 25, redone) (SP-20260615-002)

**Sprint:** `SP-20260615-002`
**PRD:** `.claude/project/sprint/requirements/SP-20260615-002/prd.md`
**Authored by:** product-lead (design phase, ε-conducted) · **β:** DECIDE 0.88 (5 binding HOW-notes folded in, labeled [β-1..β-5]) · **Layer:** dev-tooling (node scripts + a vanilla browser GUI)

> Each AC is a testable statement with a `verified_by:` line. `verified_by` root: `tests/regression/SP-20260615-002/`.
> Two AC classes: (1) node assertions over the data layer + the served HTTP surface (the bulk — deterministic, no browser); (2) a design-quality / visual-review **gauntlet artifact** for the rendered-page "looks nice" bar (R-6), which requires the page actually served + reachable. Where an AC can only be proven by the live rendered page, its `verified_by` names the gauntlet artifact under `runtime/sp002-roadmap-gui/` AND a node fallback over the served HTML where one is meaningful.
> READ-ONLY v1 is a hard boundary (β-3): every write endpoint that `scripts/dispatch/gui.js` carries is ABSENT here — asserted by presence-of-absence, not just "unreachable". No new runtime dependency is introduced (β-2). Loopback+token security carries over verbatim (β-5). Fail-soft extends to the two NEW data areas (β-4). The false-green risk on the gauntlet is closed by a keepalive flag + an exact-URL-off-stdout contract + a real-rendered-board assertion (β-1).

## S-1 — Data aggregator: four complete data areas, fail-soft (R-1)

- AC-R1a (epics area, parsed + fail-soft per epic): Given the aggregator runs against a `--root` fixture whose `trackers/epics/*.md` files carry the parseable fields, when `generate({root})` is called, then `summary.epics` is an array where each entry has `{ id, title, state, percent, childSprints[] }` — `state` parsed from the `**Current state:**` line, `percent` from the leading number on the `**Percent completion:**` line (null if unparseable, never a throw), and `childSprints` from the `## Related sprints` list. A SINGLE malformed/renamed epic file degrades **only that epic** (it is dropped or marked `{ parseError }`) and adds `"epics"` to `sectionsUnavailable[]` ONLY when the whole `trackers/epics/` directory is unreadable/absent — one bad file never blanks the area. [β-4]
  verified_by: tests/regression/SP-20260615-002/aggregator-epics.test.js::epics-parsed-state-percent-childsprints-one-bad-file-degrades-only-itself
- AC-R1b (per-sprint ticket breakdown, parsed + fail-soft per sprint): Given a `--root` fixture with sprint records at `.claude/project/sprint/sprints/<id>/current.yaml`, when `generate({root})` is called, then `summary.sprintBreakdown` maps each in-flight sprint id to its ticket breakdown derived from the `tickets:` state-column map (`{ done[], in_progress[], in_review[], blocked[], ... }`) plus per-state counts and a total. A sprint whose record is missing/unparseable degrades to `{ id, breakdownUnavailable: true, reason }` for that one sprint (and is surfaced as such), never throwing and never blanking the other sprints' breakdowns. [β-4]
  verified_by: tests/regression/SP-20260615-002/aggregator-ticket-breakdown.test.js::breakdown-per-sprint-from-tickets-map-one-bad-record-degrades-only-itself
- AC-R1c (four areas present + backward-compatible): Given a fully-populated `--root` fixture, when `generate({root}).summary` is read, then it contains ALL FOUR named data areas the operator asked for — (a) `inFlight`/`activelyExecuting` active sprints with `{ id, status, phase }` and (where derivable) ticket counts, (b) the prioritized `ranked` roadmap order + `hasPickupQueue`, (c) `epics`, (d) `sprintBreakdown` — AND the v1 fields (`nextAction`, `ranked`, `inFlight`, `gaps`, `sectionsUnavailable[]`) are still present and unchanged in shape, so the existing `--text` board and the v1 regression suite stay green (extend, do not break).
  verified_by: tests/regression/SP-20260615-002/aggregator-shape.test.js::summary-has-four-areas-and-v1-fields-unchanged
- AC-R1d (read-only + exit-0, extended to new sources): Given the aggregator runs (CLI `--json` and library `generate()`), when it touches ANY source incl. the two new ones (`trackers/epics/`, sprint records), then it performs NO write/append/rename to ANY file (proven by a before/after mtime+content snapshot of the fixture tree), the CLI exits 0 even with several sections degraded, and a phase that is genuinely absent in a source is reported as such rather than invented (`evidence-over-invention`). [β-4]
  verified_by: tests/regression/SP-20260615-002/aggregator-readonly.test.js::no-source-mutation-across-all-sources-exit-0-on-degraded

## S-2 — Browser GUI server: gui.js safety pattern, read-only, keepalive for review (R-2)

- AC-R2a (loopback + token + OS-port + headers carried over verbatim): Given `scripts/panel/roadmap-gui.js` starts the server, when it is probed, then (i) it binds `127.0.0.1` on an OS-chosen port (`listen(0)`), (ii) a non-loopback `remoteAddress` gets **403**, (iii) every path WITHOUT the 256-bit hex token (`crypto.randomBytes(32)`) gets **404**, and (iv) every response carries `cache-control: no-store` + `x-content-type-options: nosniff`. These mirror `scripts/dispatch/gui.js` exactly. [β-5]
  verified_by: tests/regression/SP-20260615-002/gui-security.test.js::loopback-403-token-404-osport-nostore-nosniff
- AC-R2b (READ-ONLY — write endpoints ABSENT, presence-of-absence): Given the running server, when each of `POST /<token>/api/save`, `POST /<token>/api/revert`, `POST /<token>/api/preview`, and ANY non-GET method on a data route is requested, then it returns 404/405 (not 200) — AND a static assertion over `scripts/panel/roadmap-gui.js` source confirms it neither `require`s nor references the write modules (`./save`, `./backup` / `applySave` / `restoreBackup` / `createBackup`) and declares no mutating route handler. The ONLY data route is `GET /<token>/api/board`; the ONLY other GET routes are `/<token>/` (HTML) and `/<token>/api/health`. A planted write handler FAILS this AC. [β-3]
  verified_by: tests/regression/SP-20260615-002/gui-readonly-endpoints.test.js::write-endpoints-absent-not-merely-unreachable-only-get-board-served
- AC-R2c (exact URL on stdout + review-mode keepalive — closes the false-green race): Given the server starts, when it has bound, then it prints the EXACT reachable URL `http://127.0.0.1:<port>/<token>/` to stdout in a stable, machine-readable line (the review harness reads the port+token off this line — it NEVER guesses the port). AND given `--review-mode` / `--no-auto-shutdown` is passed (or `WARPOS_GUI_KEEPALIVE` is set), the auto-exit lifecycle (stdin-EOF / tab-close `beforeunload` ping / the 3s soft-shutdown timer) is DISABLED so a headless gauntlet cannot race the server dead before/while the page renders; the server stays up until SIGINT/SIGTERM. In normal (non-review) mode the gui.js clean-shutdown behavior is preserved. [β-1]
  verified_by: tests/regression/SP-20260615-002/gui-lifecycle.test.js::prints-exact-url-on-stdout-AND-review-mode-disables-autoshutdown
- AC-R2d (no new runtime dependency): Given `scripts/panel/roadmap-gui.js` and any new modules it adds, when their `require()`s are statically enumerated, then they resolve ONLY to Node built-ins (`node:http`, `node:crypto`, `node:child_process`, `node:path`, `fs`) + first-party repo modules (notably `scripts/panel/roadmap.js#generate`); `package.json` dependencies are unchanged (no new entry). A vendored/npm UI framework FAILS. [β-2]
  verified_by: tests/regression/SP-20260615-002/gui-no-new-deps.test.js::server-requires-only-builtins-and-firstparty-package-json-unchanged

## S-3 — Visual frontend: polished, four areas, no framework (R-3)

- AC-R3a (all four data areas render from the fetched JSON, with known selectors): Given the page is served and `GET /<token>/api/board` returns a fully-populated payload, when the DOM is inspected, then FOUR labeled regions are present and non-empty — `[data-area="active-sprints"]`, `[data-area="roadmap"]`, `[data-area="epics"]`, `[data-area="sprint-breakdown"]` — each rendering its data as cards/columns/progress (NOT a raw text dump); epics render a visible progress indicator reflecting `percent`. These stable `data-area` / card / column selectors are a CONTRACT the R-6 gauntlet asserts against. [β-1]
  verified_by: tests/regression/SP-20260615-002/frontend-areas.test.js::four-data-area-selectors-present-and-populated-from-board-json
- AC-R3b (vanilla payload — no framework, design-system-aligned): Given the served HTML, when its `<script>`/`<link>` and markup are inspected, then there is NO external/CDN/framework asset (no React/Vue/Tailwind/CDN `<script src>`); the page is self-contained vanilla HTML/CSS/JS served inline by the server (the Dispatch Console idiom), and it reuses the established design-system token palette (the `--bg/--surface/--text/--primary/--border/--success/--warning/--error` CSS-variable vocabulary from `scripts/dispatch/gui.js`) rather than ad-hoc hex. [β-2]
  verified_by: tests/regression/SP-20260615-002/frontend-vanilla.test.js::no-external-or-framework-assets-design-system-tokens-present
- AC-R3c (escaping — human-authored source is untrusted): Given an epic title / sprint title / ranked-item text containing HTML metacharacters (`<`, `>`, `&`, `"`) in the board payload, when the frontend renders it, then the value is escaped (mirrors gui.js `escapeHtml`) so a `<script>`-bearing title in a tracker file cannot inject into the panel — a planted metacharacter title renders as text, not markup.
  verified_by: tests/regression/SP-20260615-002/frontend-escaping.test.js::tracker-authored-html-metachars-are-escaped-not-injected

## S-4 — Interactivity: client-side, read-only (R-4)

- AC-R4a (filter + expand/collapse + drill, 100% client-side over fetched JSON): Given the loaded page, when the operator (i) filters (e.g. by sprint status / epic state), (ii) expands/collapses a section, and (iii) drills into a sprint or epic to see its detail (the sprint's ticket breakdown / the epic's child sprints), then each interaction mutates ONLY client-side view state over the already-fetched board JSON and issues NO network write — the only network calls the page ever makes are `GET /<token>/api/board` (load/refresh) and the `GET /<token>/api/health` ping. A POST/PUT/PATCH/DELETE originating from any interaction FAILS this AC. [β-3]
  verified_by: tests/regression/SP-20260615-002/frontend-interactivity.test.js::filter-expand-drill-mutate-only-client-state-no-write-calls
- AC-R4b (drill-into-detail shows the right child data): Given the four areas are populated, when the operator drills into a specific epic, then the detail view shows THAT epic's `childSprints` and `percent`; when they drill into a specific in-flight sprint, the detail shows THAT sprint's ticket breakdown (the `tickets:` state columns from R-1b) — i.e. the drill target's identity threads correctly to the rendered detail (no cross-wiring).
  verified_by: tests/regression/SP-20260615-002/frontend-drill.test.js::drill-target-identity-threads-to-correct-detail

## S-6 — "Looks nice" gauntlet: real rendered board, fail-not-skip (R-6)

- AC-R6a (design-quality / visual-review against the ACTUALLY-served page — false-green closed): Given `roadmap-gui.js` is started in `--review-mode` (keepalive on, per R2c) and the harness has read the EXACT `http://127.0.0.1:<port>/<token>/` URL off its stdout (never a guessed port), when the design-quality / visual-review agent navigates that URL, then it asserts a REAL rendered board — the known card/column selectors are present (the `[data-area="..."]` contract from R3a) AND **all four data areas are visibly rendered** — and it verifies the panel is visually polished against the design-system (token palette, spacing, legible hierarchy, the "it must look nice" bar). A navigate-failure, a blank/empty DOM, a missing data area, or an unreachable server is a **FAIL — never a skip / never an auto-GREEN**. [β-1]
  verified_by: runtime/sp002-roadmap-gui/visual-review.json (design-quality/visual-review gauntlet artifact: `ok:true` + navigated to the exact stdout URL + the four `[data-area]` selectors asserted present + visual-polish verdict PASS; navigate-fail/blank-DOM recorded as FAIL). Liveness-bound (the same `ok:true` record `gauntlet-verify` reads); blank/blocked → fail-closed.
- AC-R6b (interactions verified on the live page): Given the live reviewed page, when the gauntlet exercises one filter, one expand/collapse, and one drill-into-detail, then each visibly updates the rendered DOM (the interactivity of R-4 is demonstrated end-to-end on the served page, not only in a unit stub), and no console error / unhandled rejection is thrown during the interactions.
  verified_by: runtime/sp002-roadmap-gui/visual-review.json (same artifact: an `interactions` block recording filter/expand/drill each produced a DOM delta + zero console errors; absence of the block or a thrown error → FAIL).

## S-7 — Cold/degraded-data path renders, never a blank or thrown board (R-1 + R-3 cross-cut) [PL principles: ftue-nux / cold-vs-warm-start]

> Authored-in by the product-lead. For THIS panel, "cold start" is not a new human user — it is **empty/degraded data** (no active sprints, an unparseable or missing source, an epic with no child sprints, a sprint with no ticket record). β-4 makes the generator fail-soft; this section makes the GUI's cold path a verified, first-class state so the panel never silently ships a blank board at the exact moment the operator opens it to "see where we are". The warm (fully-populated) path is covered by S-1/S-3/S-4; this names the cold one explicitly.

- AC-R7a (empty/cold data → a clean, labeled empty state, not a blank or crash): Given a `--root` fixture where active-sprints is present-but-empty, `epics` is empty, and `sprintBreakdown` is empty, when the board JSON is served and the page renders, then each of the four areas shows an explicit, legible "nothing here yet" empty state (not a blank region, not a spinner-forever, not a thrown error), and the page still renders its shell/header — proving the cold path is designed, not incidental.
  verified_by: tests/regression/SP-20260615-002/frontend-cold-empty.test.js::empty-data-renders-labeled-empty-states-shell-intact
- AC-R7b (degraded sources → per-area "section unavailable", whole board survives): Given a `--root` fixture where one or more sources are malformed (e.g. a corrupt epic file, an unreadable sprint record, a renamed ROADMAP marker), when the board renders, then the affected area(s) render a per-area "section unavailable" placeholder driven by `sectionsUnavailable[]` / the per-item degrade markers (R-1a/b), while every healthy area renders normally and the server still returns 200 for `/api/board` — a single degraded source NEVER produces a 500 that blanks the whole panel. [β-4]
  verified_by: tests/regression/SP-20260615-002/frontend-degraded-sections.test.js::degraded-sources-render-section-unavailable-healthy-areas-intact-200-not-500
