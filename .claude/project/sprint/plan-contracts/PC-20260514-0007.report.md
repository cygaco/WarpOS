## Original Request (verbatim)

> Make turbo.md an argument for modes (solo, adhoc, and oneshot).

## Interpreted Intent

Compose /turbo with each /mode:X skill so the operator can enter a mode AND pre-authorize batch actions in a single command (e.g. /mode:adhoc --turbo). The turbo argument optionally accepts the same scope/ttl/reason knobs /turbo already has. Mode skill bodies invoke scripts/turbo/apply.js when the flag is present; behaviour without the flag is unchanged.

## Desired Outcome

Operator enters a mode and is immediately ready to drive a batch — no second command needed to remove permission-prompt cadence for routine actions. The cross-skill composition is honest (turbo remains its own skill), and the safety floor inside apply.js + authorization-gate.js is unchanged.

| .claude/commands/mode/solo.md | verified_from_repo | Short 3-step skill body. Needs an Inputs section + --turbo arg + invocation of scripts/turbo/apply.js after mode-set CLI succeeds. |

## Current Behavior

- Evidence level: `verified_from_repo`
- Three separate skills. Operator runs /mode:adhoc, then /turbo as two consecutive commands. Each is a distinct keyboard cadence. Turbo state lives in .claude/runtime/authorization.json + a permissions.allow merge in .claude/settings.json, both managed by scripts/turbo/apply.js.

## Desired Behavior

/mode:<solo|adhoc|oneshot> [--turbo [--scope <csv>|all] [--ttl <duration>] [--reason "<text>"]] enters the mode AND applies a turbo authorization in one command. Without --turbo, mode skills behave exactly as today (no regression). With --turbo and no further args, each mode supplies a sensible default scope appropriate to its workload. The standalone /turbo skill (apply, --off, --status) remains the canonical interface for ad-hoc adjustments after mode entry.

## Scope

- Size: `s`
- Risk: `low`

### Variants

- **Minimal safe:** Document the cross-invocation pattern only — add a 'Combine with /turbo' note to each mode skill that tells operators to run /turbo as a second command. No CLI arg added. Zero engineering risk, but the operator still types two commands.
- **Recommended:** Add --turbo (+ pass-through --scope/--ttl/--reason) to all three mode skills. Skill bodies invoke scripts/turbo/apply.js after the mode-set CLI succeeds. Each mode declares a default scope set (solo=conservative, adhoc=builder-friendly, oneshot=delta-friendly with longer TTL). Document the per-mode defaults in each skill body. No changes to apply.js or mode-set.js — composition lives in skill bodies.
- **Expanded:** Recommended + (a) record turbo state in the mode marker (mode-set.js writes a 'turbo: { scopes, expires_at, started_by }' sub-object); (b) auto-clear turbo on mode exit (mode transitions trigger turbo --off if the same mode started it); (c) per-mode turbo defaults live in a small JSON registry so they're declarative not buried in prose; (d) /turbo --status surfaces 'started by /mode:X' provenance.
