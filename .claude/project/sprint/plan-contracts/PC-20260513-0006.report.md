## Original Request (verbatim)

> I am scared to update other projects to newer versions because there is always issues and tons of troubleshooting. Harden updating.

## Interpreted Intent

Reduce the failure rate (and emotional cost) of /warp:update when applied to downstream projects. Identify recurring failure modes from session + event history, add preflight gates that prevent unsafe applies, wrap the apply phase transactionally with rollback on any failure, and verify the install postflight before declaring success.

## Desired Outcome

Operator runs /warp:update on a downstream project and trusts the outcome: either the update completes cleanly with evidence (manifest honesty, path resolution, providers, structure parity), or it stops before damaging anything and tells the operator exactly what to fix.

## Current Behavior

- Evidence level: `verified_from_repo`
- update.js has been substantially rewritten across 0.1.2 → 0.5.0 (fixing sourceTreeRoot, migrations, postUpdateChecks, MERGE_SAFE, adding a transaction record). Multiple /check:warpos-* skills exist (manifest-honesty, applied-migrations, staleness, structure-parity, tracked-transients, path-resolution, roundtrip stub, promote-coverage stub, promote-scope, migration-coverage stub). Operator still reports recurring troubleshooting — implies the gates exist as skills but aren't composed into the update lifecycle, OR they don't catch the actual failure modes hit in practice.

## Desired Behavior

/warp:update runs three phases: (1) preflight — compose /check:warpos-* gates and refuse to apply if any block; (2) transactional apply — snapshot files that will be touched, apply, validate, commit-or-rollback; (3) postflight — run /warp:health + provider-smoke (if Plan 2 ships) + path-resolution + manifest-honesty + applied-migrations. Failures roll back. Success prints structured evidence.

## Scope

- Size: `l`
- Risk: `high`

### Variants

- **Minimal safe:** Add a preflight phase to update.js that composes every existing /check:warpos-* gate. Block apply if any gate is red. No apply-time changes, no rollback work.
- **Recommended:** Above + a transaction wrapper around apply (snapshot files-to-be-touched + transaction id, apply, validate, commit-or-rollback) + a postflight verifier (composes /warp:health + provider-smoke if Plan 2 ships + path-resolution + manifest-honesty). Failures stop with rollback. Postflight failures are reported, can opt to rollback or accept-with-warnings.
- **Expanded:** Above + a migration-replay test bench (every capsule applies cleanly to a synthetic clean install AND common drift states), a /warp:update --dry-run --verbose-rca mode that surfaces every failure mode pre-emptively, a recurring-failure dashboard hooked to events.jsonl, integration with /issues:log when a class of failure repeats.
