## Original Request (verbatim)

> A way to run multiple sprints in parallel.

## Interpreted Intent

Lift the single-active-sprint constraint baked into Sprint Workflow v0.1. Today there is exactly one current-sprint.yaml and one sprint-progress.yaml; every sprint helper reads/writes those singletons by file path. The user wants the sprint subsystem to support more than one sprint being alive at a time, and ideally to let independent sprints execute concurrently without stepping on each other's tracker state, git state, or downstream artifacts. Two senses of 'parallel' need to be disentangled during design: (a) multiple sprints OPEN at once (paused/active, but one Ralph loop runs at a time), and (b) multiple sprints EXECUTING simultaneously in separate worktrees/branches. (a) is mostly a state-shape refactor; (b) requires isolation primitives and a conflict-detection model.

## Desired Outcome

Founder can keep more than one independent piece of work in flight (e.g. a framework hardening sprint and a product feature sprint) without serializing them. Switching contexts costs a flag, not a teardown. When work streams are truly independent (different surfaces, different worktrees), both can make progress on the same calendar day.

## Current Behavior

- Evidence level: `verified_from_repo`
- Sprint Workflow v0.1 enforces a single active sprint via two singleton yaml files (paths.sprintCurrent, paths.sprintProgress). init.js writes them; every helper in scripts/sprint/ reads/writes them; the schema declares the constraint explicitly. There is no concept of 'inactive sprint' beyond moving to history/<sprint>/, no concept of lanes, and no concurrency lock on sprint-state writes.

## Desired Behavior

WarpOS supports more than one sprint coexisting at any time. At minimum, a user can have several sprints open in 'paused' state and switch among them by flag without losing tracker state. At the recommended level, two sprints can execute concurrently in isolated lanes (each lane scoped to a git worktree or non-overlapping surface set), with provider dispatch locks already arbitrating shared rate limits and a conflict-detection check refusing to launch overlapping work without an explicit override.

### Variants

- **Minimal safe:** Per-sprint state, no concurrent execution. Replace paths.sprintCurrent/paths.sprintProgress singletons with per-sprint subdirs (e.g. .claude/project/sprint/sprints/<SP-id>/current.yaml + progress.yaml). Add a top-level active-sprints.yaml registry pointing at the current set. Add --sprint <SP-id> to every helper; default to the registry's primary entry when omitted. Migrate the existing SP-20260512-001 in place. Update hooks + docs. Ralph loop still runs on one sprint at a time.
- **Recommended:** Per-sprint state PLUS concurrent execution via lanes. Each sprint declares a lane: 'default' (current worktree), 'worktree:<path>' (git worktree, reuses builder isolation primitive), or 'branch:<name>' (light isolation). /sprint:execute runs in the lane's worktree. Sprint-routing.json gains a concurrency block (max lanes, default lane, isolation default). A lane-conflict-check refuses to launch two sprints whose affected_surfaces overlap unless the user passes --allow-overlap. Beta gets a 'lane' context field; issues.md, decision-ledger, events.jsonl, beta events tag every appended row with sprint id. Sprint commands honor --sprint <SP-id> end-to-end. Add a /sprint:status that lists all active lanes.
- **Expanded:** Recommended PLUS an active sprint coordinator. A new helper (scripts/sprint/coordinator.js) watches the active-sprints registry, schedules /sprint:execute calls across lanes against a configurable concurrency budget, pauses lanes when one hits a high-risk gate (e.g. release approval pending elsewhere), and aggregates spend/telemetry. Adds a cross-sprint dependency declaration (sprint.requires: [SP-X]) so a sprint can block on another finishing. Adds a /sprint:dashboard summary view. Beta becomes lane-aware (one Beta thread per active lane, sharing precedent state).
