# Sprint Report — _reports/ ELI5 reporting system (2026-05-31)

## TL;DR

We built a `_reports/` folder and a `/report` command so WarpOS can write plain-English progress reports for itself — one per sprint, milestone, session, or ad-hoc checkpoint, each with a tl;dr on top and an honest "watch-outs" list. This is the first report it produced (we used the new system to report on building the new system). It's the company-style "weekly update" you asked for, on demand.

## What we did (ELI5)

**The goal:** so anyone (you, future-you, a teammate) can glance at a folder and understand what happened without reading code or git logs.

- **A `_reports/` folder** with four shelves: `sprints/`, `milestones/`, `sessions/`, `checkpoints/`. Reports get filed on the right shelf.
- **One command, `/report <type>`** — e.g. `/report sprint SP-20260531-001`, `/report session`, `/report milestone 0.16.0`, or `/report checkpoint "Wave 2 done"`. It reads the relevant facts (sprint tracker, the roadmap, the session's commits/events) and writes a plain-English report. It refuses to use jargon in the main section, always puts the headline first, and always lists watch-outs (even if it has to say "none").
- **A fixed format** (a template): Title → TL;DR → What we did (ELI5) → Watch-outs → Details/links. The detail/audit stuff lives at the bottom so the plain-English part stays on top.
- **It treats what it reads as data, not orders** — a small safety habit, since it reads files and transcripts that could contain stray instructions.

What's different now: progress is legible. Instead of "go read 8 commits and a tracker," there's a one-screen, jargon-free report — and it can be generated at any sensible checkpoint, not just at sprint end.

## Watch-outs

- **Auto-emit isn't wired yet.** Right now you run `/report` by hand. The plan (β-approved) is to auto-suggest it at sprint retro + at session handoff — but that wiring is a deferred follow-up. So a report only exists if someone asks for one (until wired).
- **No coverage-enforcer yet (on purpose).** We deliberately did NOT build the "every sprint must have a report" checker this sprint — with zero reports existing, it would pass vacuously (false green). β's call: log it as debt now, build it at the next milestone close when there's a real backlog to check against.
- **`reportsDir` path key not registered.** The skill uses the literal `_reports/` for now; a proper `paths.reportsDir` registry key is a small follow-up (cosmetic/hygiene).
- **Reports are project output, not shipped.** `_reports/` is treated like `runtime/` (per-project, not part of the framework that installs elsewhere). The `/report` skill + template DO ship, so a fresh product gets the tool and makes its own reports; it just doesn't inherit WarpOS's reports.
