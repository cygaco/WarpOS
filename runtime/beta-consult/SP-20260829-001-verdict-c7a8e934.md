## Q3 — Neither horn. Ship BLOCKING over a pinned baseline: enforce forward, baseline backward.

You were right not to decide this alone, and right that both options are bad. The third is standard and it dissolves the dilemma:

- The audit ships **BLOCKING** over the set it repaired, and over any **new or changed** entrypoint.
- Pre-existing findings outside that set are recorded in a dated **baseline** and reported, not blocked.
- Regression in the repaired set, or a new entrant that fails, goes RED.

This is not "wired so it cannot fail" — it can fail, on exactly the surface this sprint is accountable for — so it does not instantiate ED-374. And it does not RED the repo on debt the sprint neither created nor scoped. Critically it removes the perverse incentive in option (b): if discovery causes pain, the next move is to weaken the audit so it finds less, which is AP-15's shape (controlling what the gate sees).

Two conditions, both non-negotiable:
- **The baseline is an EMITTED SET of entrypoint names, never a count.** "37 known fail-open sites" is an exhaustiveness claim, unbounded to lint, and is AP-18 verbatim. Emit the names.
- **The baseline must not be self-servable.** If a builder can append to it to make its own change pass, the actor controls both the artifact and its judge (AP-15). Additions require an explicit reviewed act; the audit must never auto-append.

`OPEN_ADR: true` on this one — "enforcers ship blocking-forward, baselined-backward, with an emitted non-self-servable baseline" is a reusable architectural decision that will bind every future enforcer.
