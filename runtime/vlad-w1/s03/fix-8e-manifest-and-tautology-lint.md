## PART 1 — the resolved pointer manifest (β r2 Q2, five conditions)

**The defect.** `verified-by-resolver.js` reads an acceptance-criteria document that **does not exist in
the vlad repo** — it resolves out through `--ac-file` / `VLAD_AC_FILE` / a machine-local absolute path
into a sibling WarpOS directory. And the test pinning its count **`t.skip()`s when that file is absent**.
So the enforcer is real on this machine and **absent everywhere else**, while the shipped
`package.json#vladPointerLint` block reads as though it enforces generally.

β rejected the two obvious alternatives with reasons worth carrying: **vendoring the AC file** (duplicate
source, guaranteed drift, sprint scaffolding leaking into product scope) and **accepting it as a
WarpOS-only lint** (the A5 shape — a check that proves nothing in a user's install). The ruling is a
**generated manifest**: the AC file stays the single source; a manifest generated *by observing it* is
committed into the product repo; the product-side lint resolves against that, so it works on any checkout.

**E1 — source-vs-generated discipline.** The manifest is **generated by observation, never
hand-maintained**, and carries a **do-not-edit banner**. This project has been bitten by hand-edits to
generated views before; the banner is the cheap half of the fix, the generator being the only writer is
the real half.

**E2 — TWO checks, each honest about its scope. Do not merge them.**
- **Resolution check — product-side, runs everywhere.** Resolves every pointer against the committed
  manifest. This is the one that can honestly be called an enforcer in a user's checkout.
- **Staleness check — dev/WarpOS-side only.** Asserts the committed manifest equals a fresh regeneration
  from the source AC file. **It must say so in-file**: it cannot run where the source does not exist.
Merging them would recreate the exact defect — one check whose scope silently changes with the machine.

**E3 — fix skip-reads-as-pass. β called this "the more important half", independent of the option
chosen.** When the input is absent, emit an explicit **`NO_DATA`** or go **RED**. A `t.skip()` in that
position **is the defect**: the release rule states plainly that *NO_DATA ≠ pass and `t.skip()` ≠ pass*.

**E4 — keep `check:pointers` OUT of `check:ship` until the manifest lands**, with the reason recorded
in-file. `package.json` is not yours — **report the wiring owed** so the conductor can land it.

**E5 — until it lands, any claim that the pointer index is enforced carries its scope qualifier.**

## PART 2 — the tautology lint (β r2 Q3, three conditions)

**Why it exists.** Round 4 found `assert.ok(classified.every(c => c.canSpawn || true), "always true —
kept as an explicit placeholder")` — a literal tautology, self-labelled, **inside the control whose job
was proving non-vacuity**. β authorised this lint *because a review round exists this time*.

**E6 — scope to a NAMED syntactic family, listed in the rule's own header.** Exactly these:
- a constant-truthy disjunct (`… || true`)
- a constant-falsy conjunct
- an assertion whose predicate is a literal
- an `.every()` / `.some()` callback returning a constant
**NO general tautology detection.** It is undecidable, and an over-broad rule produces a false-red flood
that gets the lint disabled — which is worse than not having it.

**E7 — it is record-producing, so it carries its own TWO-DIRECTION falsifier.** A seeded tautology
fixture goes **RED**; and **removing the rule makes that fixture pass**. Both directions, per the
record-trust gate: *a record that cannot go red is not evidence, whatever it is named.*

**E8 — name its ceiling in the header.** A syntactic lint does not catch **semantic** vacuity — β's
example is round 2's F12, `AC-2.1` asserting against the implementation's own constant, which is
perfectly non-tautological syntax and still proves nothing. State that plainly so nobody reads a green
lint as "no vacuous assertions exist".
